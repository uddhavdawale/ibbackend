# Frontend Password Security Changes Report

Date: 2026-10-28
Project: Inventory & Billing Frontend
Backend dependency: ibbackend

## 1. Objective

This report defines the frontend changes required to align with backend password security behavior:
- Password hashing is performed server-side using Argon2id.
- A unique random salt is generated by backend per password hash.
- Minimum password length is 12 characters.

## 2. Confirmed Backend Contract (Frontend Relevant)

Signup endpoint:
- POST /api/auth/signup

Required password behavior:
- Frontend sends raw password in the request field currently named passwordHash.
- Frontend must not hash the password on the client.

Failure behavior:
- On password policy failure, backend returns HTTP 400 with message like:
  - Password must be at least 12 characters long

## 3. Required Frontend Changes

### 3.1 Signup form validation

Implement client-side password rule before submit:
- Password must be at least 12 characters.

UI requirements:
- Show inline validation message when length < 12.
- Disable Create Account / Signup button until valid.
- Keep backend-side validation handling even if client validation exists.

Recommended checks:
- Trim is not applied to password unless explicitly intended by product rules.
- Do not auto-modify entered password text.

### 3.2 Payload handling

For current backend compatibility, send:
- passwordHash: <raw password>

Example payload:
{
  "businessName": "Demo Store",
  "ownerName": "Owner",
  "email": "owner@example.com",
  "passwordHash": "myVeryStrongPass123",
  "role": "STORE_ADMIN",
  "phone": "9876543210"
}

Important:
- Remove any frontend code that hashes password before API call.
- Remove any salt-generation logic from frontend (not needed and should not be done client-side here).

### 3.3 Error handling and messaging

Handle signup responses:
- 2xx: show success and redirect to login.
- 400 with policy message: show user-friendly inline or toast message.
- 400 email conflict: show Email already exists.
- 5xx/network: show generic retry message.

Suggested mapping:
- If message contains at least 12 characters -> highlight password field.
- If message contains Email already exists -> highlight email field.

### 3.4 Login flow note

No frontend hashing is needed in login either.
- Send raw password over HTTPS.
- Backend verifies using Argon2id hash comparison.

## 5. Suggested Frontend Validation Rules

Minimum mandatory rule:
- length >= 12

Optional stronger UX rules (if business approves):
- at least 1 uppercase
- at least 1 lowercase
- at least 1 number
- at least 1 special character

Note:
- Optional rules should only be enforced if backend is updated to match, otherwise frontend/backend mismatch will occur.

## 6. QA Test Cases

### Functional

1. Password length 11:
- Signup button disabled or validation shown.
- No API call should be made (preferred).

2. Password length 12:
- Signup request sent.
- Success if other data valid.

3. Backend returns 400 password message:
- Message displayed near password field.

4. Backend returns 400 email exists:
- Message displayed near email field.

5. Login with valid credentials:
- Works without client hashing.

### Security

1. Confirm no password hash function runs in browser code.
2. Confirm no generated salt in browser code.
3. Confirm password not logged in console or analytics.
4. Confirm HTTPS-only API base URL in production.

## 7. API Evolution Recommendation (Optional)

Current request field name passwordHash is semantically confusing because frontend sends raw password.
Recommended future API cleanup:
- Rename request field from passwordHash to password.
- Keep temporary backward compatibility for both fields during migration window.
