# SQL Injection Security Checklist

## Overview
This project should treat all database access as parameterized and safe by default. Any future database query must be reviewed for injection risk before it is merged.

## Safe patterns to keep using
- Spring Data repository methods such as `findBySku`, `existsBySku`, `findByEmail`, `findByOwnerName`
- `@Query` with bound parameters using `:paramName`
- Prepared statements generated by JDBC or `JdbcTemplate` with `?` placeholders
- Repository-based access rather than string-built SQL

## Unsafe patterns to avoid
- String concatenation in SQL queries
- Building SQL with untrusted input like `"SELECT * FROM users WHERE name = '" + username + "'"`
- Dynamic native queries assembled from request values
- Executing raw SQL from uploaded CSV or frontend input without validation

## Examples of safe vs unsafe usage

### Safe
```java
Optional<User> findByEmail(String email);
@Query("SELECT u FROM User u WHERE u.email = :email")
Optional<User> findByEmailParam(@Param("email") String email);
```

### Unsafe
```java
String sql = "SELECT * FROM users WHERE email = '" + email + "'";
```

## Review checklist before adding a new query
- Is the query built from user input?
- Is the query using string concatenation?
- Is there a raw `JdbcTemplate` SQL string without parameters?
- Does the code use `@Query` or repository methods instead of dynamic SQL?
- Is the input validated before being used in the query?

## Defensive rules for this project
- No raw SQL should be built from frontend or uploaded file values.
- Always use parameter binding for dynamic values.
- Keep validation in place before any data enters persistence logic.
- Prefer repository methods over custom SQL when possible.

## Practical enforcement
- Review every DAO / repository change for raw SQL usage.
- Add a test for any new query path that accepts user-controlled values.
- Never use `Statement` or concatenated strings for dynamic SQL in this backend.
